# The questions

Each question is a property a change can break without any test noticing. For every site it looks at, proofscan answers one of three ways:

- proven: the property holds, under the assumptions listed with the answer;
- violated: a concrete witness shows it failing (a path through calls, a line, a frame);
- unknown: something the model does not follow stands in the way, and the answer names it.

Every answer says which kind of reasoning produced it. Proven by the model means the facts the extractors collected and the Datalog rules derive it. Heuristic means a shape or a name decides it, and the answer is only as good as the pattern. Unknown names the construct.

Facts come from tree-sitter parses of Python, Rust, JavaScript, shell and PowerShell. They are calls, assignments, comparisons, returns, conditions with their exits, loops and handlers, string literals, imports and class bases. Calls resolve to in-repo functions. An exact edge has a known binding: a local or imported def, `self` and its bases, a qualified path, or an attribute every assignment of which constructs one class. A may edge is a match by method name within the caller's repository; a name that more than 8 in-repo methods share is not followed, and each question counts those calls under what it did not check. A witness that needs a may edge says so. Edges stay in the caller's language; a Rust bare name stays in its crate, and an edge between repositories in a sweep needs an import or a qualified path. Value kinds (clock reading, monotonic reading, outside time, outside input, public parameter, closed) flow through assignments, returns and argument binding, and an Ascent program runs them to a fixed point.

## 1. One source per fact

Proves: within one decision, each provider of a fact (the wall clock, an environment variable by name, an HTTP endpoint by path) is read once. A decision is a function with the readings that arrive in it as values: its own reads, and a callee's when the callee returns a value derived from a source. A reading a callee uses and does not return is that callee's decision. A monotonic reading measures elapsed time and a deadline loop reads it every turn, so it is not a single fact. A clock reading is never compared with a time parsed from outside without being brought to that source's precision. A test double does not re-implement the rules of the production function it stands in for.

Rules:

- `one-reading` (model). Two reads of a single-fact provider reach one decision. Violated on exact edges; unknown when the second read needs a may edge. A read passed straight into a reporting call (`q1.report`: print, a logger method, `format!`, `echo`, `Write-Host`) decides nothing and is not counted; a read assigned first and then only logged still is. A shell command outside `$(...)` writes to output and reads nothing into the script. A converting call given an argument (`q1.argless`: `new Date(x)`, `time.localtime(x)`) is no read. An environment read whose key is not a literal is its own fact. A function that reads a provider more than once on purpose (a cheap filter before a lock, then the reading the decision uses) is accepted in `q1.accepted_reading` by function label, provider and the number of read sites in its reach, with a reason: its sites are proven with that reason while the count holds, and one more reading in its reach makes them violated again. A line number is not the key, so edits above it do not undo the acceptance.
- `mixed-time-sources` (model plus patterns). A compare whose one side carries a clock kind and whose other carries outside time. Proven when the clock side passed through a `q1.normalize` call; that is an assumption, named by the call.
- `double-reimplements` (heuristic). A method of a class named like a double (`Fake*`, `*Stub`, a trait impl in test code) shares at least `double_shared_tokens` decision tokens with the production function of the same name. Tokens are the names, strings and numbers other than 0 and 1 in its conditions, and the literals it returns. The double is a second source only when one of its branches reads a parameter: a fake whose branches read only its own state (`match &self.canned`) returns what the test set, and is reported proven with that assumption even when it shares the result variants. A double that decides from a parameter in a way the scanner does not see as a branch (a lookup table indexed by the input) is missed.

Assumptions: provider patterns name every read; a call with no in-repo target neither reads a provider nor calls back; a callee that returns no sourced value does not pass a reading back through a parameter or attribute.

Known unknowns: `getattr`, `eval`, `exec`, `importlib`, `Invoke-Expression` and `source` of a computed path (rule `model-limit`); calls through a value whose type the model does not know.

## 2. Provenance of stand-ins

Proves: a fixture literal of a declared wire (`[[q2.wire]]`, a pattern plus captures) has the shape of some real capture, field by field (character class and length per comma field). No suite-wide fixture switches off a production guard.

Rules:

- `wire-provenance` (model over declared captures). A test literal matching the wire pattern whose shape no capture has. Without a declared wire nothing is checked, and the question says so.
- `suite-disables-guard` (heuristic). An `autouse` fixture that `setattr`s or `patch`es a name matching `q2.guard_names`. The answer notes whether a test can opt out.
- `upgrade-shape` (model over store identity, on a diff only). A key the change starts reading (`doc["k"]` or `doc.get("k")` on a changed line of a non-test Python file, with `"k"` nowhere in the base) from a stored document: a variable assigned from a call to a function that returns a parsed store (a return that is `json.load`, `json.loads`, `yaml.safe_load` or the like, a variable assigned from one, or a call to such a function), directly, through one assignment, or through a parameter bound to such a variable at a call site, by position or keyword. A function that names a store and returns what it computed (a run's report) is not a reader, and `doc["k"] = v` writes. Proven when a test writes one of those stores from a dict literal that lacks the key and spreads nothing (`{**current, ...}` is today's shape): that literal is the previous release's file. Violated for a subscript read without one: an old file raises there and only production loads one. Unknown for a `.get` read without one: the default answers for an old file, and nothing shows it is right. A store whose file name or constant the base does not have is new in the change, and is skipped: the previous release left no such file.

Assumptions: wire patterns name every literal that stands in for a reply; a file under a declared capture path came from the real thing.

Known unknowns: fixtures built at run time (formatted strings, files read in the test) are not literals and are not checked. `upgrade-shape` sees a new key by name, not a changed format of an existing one: ha-loops ca612a7 re-keyed the ledger's `slots` from local dates to UTC instants, and the test of a 0.15.0 ledger came only in 3a7ab95; the rule reads that change proven, since `lost_at` is the only new key and a literal without it exists. It also does not tell a test that loads the previous shape with the live configuration (ha-loops `UPGRADES`, the 0.14 state under America/Chicago) from one that loads it under any: the shape is present at f39b71d, and the 0.15.0 first-start defect was in what the code did with it. A store opened through `Path(root) / NAME` is not identified (the constant must be an argument of a path call).

## 3. Check and use together

Proves: a value a guard verified is the value the effect uses. The rule `reread-after-check` flags a predicate call whose callee reads a fact, followed (dominated, same function) by an effect whose argument reads the same fact again. The read the effect uses was never the one checked.

Assumptions: a guard reads what it verifies through calls the model sees; effect patterns name every effect.

Known unknowns: a guard reached through dynamic dispatch; a check whose read is outside the repository. The inline form, a condition and an effect that each read the clock, is Q1's `one-reading`.

Rule `stale-write-back` (model over store identity). A value read from a store and written back is the same check-and-use pair across a write: `raw = store.state()`, then a call that can write the store, then `save(raw)` or a value built from it. What the call in between wrote is overwritten with the older copy. Store identity is a file-name literal a function passes to a call (`state.json`) or a module constant naming one (`RUN_LOG = "runs.jsonl"`) given to a path call; a function writes a store when it names it and makes a write call (`q3.store_write`, not through a local such as a list's `append`). Both close over the calls a function makes; a call dispatched by method name counts only inside its file. "Between" is `falls_to`: the call comes after the read and before the write on one pass, with no unconditional return, raise, continue or break after it in a block that holds it. A second read of the same store into the value starts a fresh snapshot. Proven when a read and its write back exist with no writer between them, under the assumption that no other thread or process writes the store in between (a second thread is not modeled).

Rule `read-before-check` (model over what a guard vouches for). A check can vouch for a provider without reading it: `clock_unsynced()` asks the Supervisor whether the clock is synced and reads no clock. `q3.vouch` maps a provider to a pattern; a function whose name, or one of whose calls or string arguments, matches it checks that provider, and a predicate call that reaches such a function is a guard for it. An effect the guard dominates (an effect call, a call that reaches one, or a store writer) whose argument holds a reading of that provider must take it after the check: violated when the variable is a parameter (the caller read it, before the check) or is assigned before the guard; proven when an assignment the guard dominates dominates the effect. A clock stepped between the reading and the check is acted on as if checked. Assumptions: the vouch patterns name every status check; a reading passed in through a parameter was taken by the caller before the call.

## 4. Guard at the effect

Proves: every path from an entry point (a registered service action, a route handler, a CLI command; profile and config `q4.entry`) to an effect passes a guard call that dominates the effect or the call leading to it. The witness is the path from the entry to the effect. An entry spec can limit the effect kinds its guard covers (the Home Assistant profile's administrator rule covers registry writes only; the integration's own store is its own state).

Rule `unguarded-effect` (model). Violated on exact edges. Unknown through a may edge.

Assumptions: entry, guard and effect patterns are complete; a guard raises or exits early when its check fails.

Known unknowns: handlers registered through a dynamic table; effects behind dispatch by name.

Rule `write-before-guard` (model). A guard that vouches for a provider (as in Q3's `read-before-check`) refuses to act on an unchecked reading, so a call that runs before it (dominates it, same function) must not write a store with a reading of that provider: violated when the call reaches a store writer and a reading of the provider, either a provider source or a call whose result is of the provider's kind (`self.now()` holding an injected clock). What the check would refuse is already on disk. An order kept on purpose goes in `q4.accepted_order` (`site` as `path:line`, or a function label covering every such write in it, and `reason`) and is reported proven with its reason. Assumptions: the store writer named is the one the reading reaches; a reading and a write in the same reach are one value.

Rule `guard-after-wait`. For strings from Axum route bodies, a size check that returns early should run before an awaited Tokio semaphore acquisition. The rule follows the handler, one awaited forwarding call, and a local queue method that runs an inline callback after acquiring a permit. The callback can call a local checker. It reports violated when the visible path acquires the permit before the size check and has no earlier bound. A returning check that caps the same input before the wait is proven. Its location and byte limit are named in the assumptions. A conditional or opaque earlier check or an unresolved limit gives unknown when there is a candidate late check.

Assumptions: the registered extractor supplies untrusted input, immutable string copies preserve byte length, and collecting a filter over the string's characters can only reduce that length. The proof covers the named route path and semaphore wait. Known unknowns include framework or middleware limits, dispatch through traits or macros, other queue or lock APIs, deeper call chains, and bounds on decoded or otherwise transformed payloads.

## 5. Closed sets

Proves: a value spliced into a path or URL segment is a constant, or was parsed into a closed set first (`int`, `UUID`, `fullmatch`, a quote function: `q5.closed_parse`), or the composed path is checked to stay under its root (`resolve().parent ==`, `is_relative_to`, `commonpath`) before use. No refusal is decided by a deny pattern.

Rules:

- `closed-segment` (model). A public parameter or outside input reaches a segment unparsed. When a refusing test filters it (a deny test that is not a closed parse), the witness names that test, because a list of refused forms is still an open set (`C:x` passes a test that refuses `/` and `..`).
- `open-deny` (heuristic by shape). An `if PATTERN.search(x): refuse`, a membership test against a deny-named collection, or a branch that records a refusal reason (`hits.append(...)`). A deny list accepted on purpose goes in `q5.accepted_deny` with its reason, and is reported proven with it.
- `name-table-guard` (heuristic by shape). A structural test (one in a file that walks a syntax tree: `ast.walk`, `ast.parse`, `getsource`) whose check is gated by membership in a hand-kept table: a module constant holding a literal set, tuple, list or dict, or a literal set inline. `if name not in TABLE: continue` checks only the listed names, and `if name in TABLE: <record a violation>` refuses only them; code added later outside the table passes. Proven when the membership closes the set: `if name not in ALLOWED: <record a violation>`, or `if name in ALLOWED: continue`. The fix the rule points at is to enumerate by the primitive (the write call, the clock read) and allow-list the functions where it may appear. A `return` from a helper is not taken as a skip, since it may be the detection itself. Every membership in a condition is judged, once per left side and table. Which names the table holds decides the verdict:

  - A test whose left side does not come from a syntax-tree name field (`.name`, `.id`, `.attr`, `.module`, `.arg`, directly, through a variable assigned from one, or through a same-file helper that returns one) tests a value (`r.status_code in (200, 201)`, a parsed SQL keyword) and draws no finding.
  - Bound names (`Name.id`, a parameter's `.arg`) are violated whatever the table holds: an import alias or a rename makes a name the table never saw (`from datetime import datetime as DT`).
  - A table more than half of whose names this repository defines (a function, class or file name in the same repository) is violated: it grows with the code.
  - A table of mostly outside names (stdlib modules, a library's operations or constructors) matched by a field an alias cannot change is proven, assuming the table holds the whole outside domain: a new member is a fact about that library.
  - With no production code in the scan (a `tests`-only scope), whose names they are is unknown.

- `text-filter-pass` (Rust subprocess diagnostics). Asks when a line matched by substring, prefix or regex is dropped from a count that rejects the check, or when a subprocess wrapper withholds error lines while forwarding the remaining diagnostics. Tracks captured stdout and stderr through local bindings and same-file buffered readers. Violated when the matching lines are dropped without checking their identity or count. Proven when the complete line also belongs to a literal allowlist, or the counter for this branch starts at zero, increments once per drop and is checked against an independent count before a successful return. The proof assumes that the listed lines or count represent the expected exceptions, that the counter does not overflow, and that callers honor a returned error. Unknown when an additional predicate or a consumer of the discarded-line count decides the allowance and the rule cannot establish its effect. The check covers the diagnostic filter. A wrapper can still propagate the child's exit status while hiding diagnostics.

Assumptions: a parameter of a public function is outside input; closed-parse patterns accept only members of a closed set.

Known unknowns: values that cross a process or file boundary before the splice. For `text-filter-pass`, iterator adapters that filter without a loop, checks in other files, and package identity inside general parsing helpers are outside the model.

## 6. Bounds and exits

Proves: every state has an exit.

Rules:

- `wall-date-bound` (model). A kept collection pruned by a bound derived from the wall clock, then written back. A clock step drops or keeps everything.
- `retry-limit` (local loop bounds and progress). A retry runs a fallible operation again on the same input after an error. The rule checks Rust, Python, JavaScript, Bash and PowerShell. A counter or deadline proof names the comparison and its line. The comparison must control a loop condition or an exit visible in the loop body, and each continuing path must pass the check and the counter update or fresh clock read. An exit can be a `break`, a function return, a raised error, or a Rust `?` that visibly propagates an error.

  Counter proofs use a local integer initialized before the loop and a step in the direction of the bound. They assume ordinary integer arithmetic, a fixed limit, no overflow or loss of precision before the exit, and no hidden rebinding by calls. Deadline proofs use recognized clock reads such as Rust `Instant::now()`, Python `time.monotonic()`, JavaScript `performance.now()` or `Date.now()`, or Bash `SECONDS`. They assume the standard clock, a finite fixed limit in the clock's units, and that the clock advances past it and intervening operations return. A Rust bounded range or Python `range(n)` supplies its own progress, assuming the standard integer iterator and finite endpoints. A visible use of the iteration index in the operation excludes that operation from the range retry check.

  A legacy keyword alone gives unknown. This includes unused counters, counters that can stay fixed or be reset, comparisons that only log or set a backoff, and checks whose effect is hidden inside a helper or closure. The message gives the keyword and says no exiting comparison establishing a bound was found. The rule uses direct local guards and steps, so some valid bounds inside branches, match guards, macros or calls are still unknown. A detected retry with neither a legacy keyword nor a bound remains violated. Bounded loop shapes outside the legacy detector can add a proof.

  The Rust progress proof covers a `loop` over a direct match of `std::str::from_utf8` on a local byte slice. Success must exit. Each continuing error path must replace that same slice with a strict suffix of its current value or of the suffix produced by `split_at` in that iteration. The proof bounds the number of back edges by the original byte length.

  The rule accepts a positive decimal literal, a bound `Some(n)` from the same error's `error_len()`, or `valid_up_to() + n` on the original slice. For `split_at(error.valid_up_to())` it also accepts `error.error_len().unwrap_or(after.len())` on the second result, `after`. The library facts are that `error_len()` supplies at least one byte whenever it is `Some`, `valid_up_to()` is the valid prefix length, and a UTF-8 error leaves a nonempty suffix after the valid prefix, including an incomplete sequence. The proof assumes standard byte-slice indexing and names the library facts it uses.

  A possibly zero offset, an unrelated slice replacing the input, or an input update whose progress cannot be followed on every path yields unknown in the modeled match shape. Slicing another variable while the call keeps reading the original input gives the Rust retry shape a violation. The input-progress argument applies to Rust `loop` expressions.

  A remaining-duration proof links a fresh Rust `Instant::now()` subtraction from a fixed deadline to the expiry exit. Saturating subtraction must be tested with `is_zero()` or against `Duration::ZERO`. Checked subtraction must exit on `None`. A computed remainder without a test supplies no bound. The standard monotonic clock must advance past the deadline and each intervening operation must return.

  A civil deadline proof links a fresh Jiff `Zoned::now()` or Chrono `Local::now()` or `Utc::now()` reading to a fixed deadline, including their supported civil-time projections. The wall clock must eventually reach and pass the deadline in the same time basis, and the operations between readings must return. A backward step can delay expiry. A clock sampled once outside the loop cannot establish this bound.

  An enumerator deadline proof combines two obligations. Each timeout back edge must pass an exiting monotonic deadline check. Every other back edge consumes an item from the same finite forward-only enumerator. The modeled WMI `Next` call must read one item from a forward-only `ExecQuery` result and leave on exhaustion. The modeled `next_for` result uses the same contract for `Ok(Some(item))`. This assumes the enumerator and clock honor their contracts and that each read and handler returns. A second failure path that bypasses the deadline leaves the bound unknown.

  A finite-width growth proof links the strict comparison of requested bytes to actual allocated bytes to the only retry's resize or replacement. The new element count rounds the same `u8`, `u16` or `u32` byte count up by the element width. The proof assumes standard `Vec` semantics, lossless byte-count arithmetic on the target, and that calls through the data pointer cannot change the vector's length. Equality, a different size source, or another continuing edge leaves the bound unproven.

  A Rust match can prove a deadline when every continuing error arm requires a fresh clock comparison before the fixed deadline. A match can also prove a finite number of retries when each continuing arm requires a previously clear local flag and sets it before any further work. Assignments elsewhere leave that flag argument unproven.

  A Rust collision probe has no retry finding when each back edge follows `ErrorKind::AlreadyExists` and the next call probes a fresh key. The rule follows a function-local static atomic's `fetch_add(1, ...)` result or a loop-carried integer advanced by one on every back edge. It follows immutable bindings to the call argument through references, decimal formatting with fixed name components, and `Path::join` on a fixed parent. It requires one probe per pass, with any other result leaving the loop. A bypass, reset, discarded counter value, or second probe with the same key leaves the retry check in place.

  This classification assumes standard atomic, formatting, path and I/O error semantics. The counter must avoid wraparound, including increments from concurrent invocations of the function. The formatted name must identify a distinct key for each index, and `AlreadyExists` must report a collision for the supplied key, including when a wrapper makes the call. The rule makes no claim about how many names are occupied or when the loop will find a free one.

  Registry reads with a nonempty byte vector can prove progress when each `ERROR_MORE_DATA` back edge grows it by at least a factor of two. The standard byte vector's capacity bounds the number of successful growth steps. For enumeration, every other continuing edge must increment the argument that selects the item and pass an exiting index cap.

  A successful `FindNextVolumeW` writes the next GUID into the buffer used by the per-volume probes. The retry detector drops only errors from operations derived from that buffer, after checking that each back edge reaches the advance and a failed advance exits. A standard `VecDeque` field drained with `pop_front` supplies fresh input to operations derived from the popped value when the loop never touches the queue again in its body. A standard `panic!` in the error arm exits the loop.

  Pending-batch delivery is violated when the same delivery ID is recorded as failed, the storage update leaves the row pending, and the selection has a batch size but no attempt cutoff. A batch whose eligibility is hidden stays unknown. Receive refusals and state changes governed by another function remain unknown where the local code exposes progress but cannot establish the bound.

  A continuing listener error inside `tokio::select!` repeats the accept on the same listener. A continuation on an HTTP error status or a failed batch whose handler rearms the same polling flag also keeps the retry candidate visible.

  A per-item replay proof follows one popped item through its error guard, flag assignment and requeue. The flag must be tested and set on that same item before it goes back onto the same queue. This assumes that the queue preserves the moved flag and that producers do not resubmit the same item as new work. A flag set after requeue or held in worker state whose lifetime crosses asynchronous branches is unproven. When the requeue is visible, the unknown finding points to the enqueue.

  A fallible read whose failure leaves the loop does not count as a retry when success moves to fresh input. The detector also recognizes discarded input lines, completed task results, and an accepted client that is closed before moving to the next connection.

  Failed work in a nested batch selected from a pending store may return in a later batch. The rule keeps that case unknown unless it can follow the per-item state across batches.
- `state-exit` (shape plus model). The newest value per key kept with no check that the key is still live.
- `durable-exit` (model). A durable resource (`q6.resource`, e.g. a cloudhook or a snapshot) made where no release is reachable from a startup, or where a start path reaches it with no sweep dominating it (see question 9).
- `handler-requery` (model). A failure handler that calls again the query whose failure it handles, so the failure state has no exit.
- `stale-status` (model over conditions and exits). A status attribute: `self.X` set to `None` somewhere and to a string or f-string (parenthesized when split over lines) somewhere, where the string is set on a refusal (a `raise`, or a `return False`, `None` or bare return within six lines after it on its path). An attempt is a function that both sets and clears it, the constructor aside. Proven when a clear dominates every set in the attempt (each attempt starts clear), when every exit of the attempt follows a set or a clear within six lines on its path (each call leaves its own outcome), or when every call site of the attempt is dominated by a clear. Violated otherwise, at the first clear: an exit that records nothing (a plan already gone, an early return) leaves the last attempt's reason showing, so the page names a reason that no longer holds. The witness names each refusal that sets it, each function the attempt reaches that sets it, the clear, and the exits that leave it as it was.
- `fixed-day-span` (pattern plus clock kind). In a repository that keeps a time zone (it calls `ZoneInfo`, `astimezone`, `tz_localize`, `timezone` or `gettz`), a call given a window from `X - timedelta(days=N)` (or `weeks=N`, or `hours=24k`) to `X`, both arguments of the same call, with `X` a clock reading. A day of wall time is 23 or 25 hours across a daylight saving change, so a window of one fixed day back misses or repeats an hour twice a year; the fix starts the window at the previous run's start (ha-loops `logbook_since`). A naive repository's day is 24 hours of its own clock and is not judged.
- `held-state-exit` (model over conditions and exits). An attribute holds a run between calls when a function returns while it is set (`if self.plan is not None: return`, a gate) and a call in that function before the gate, or inside it, reaches a clear of it (`self.plan = None`), the retry. A refusal is a `return False`, `return None` or bare return from the retry with no clear before it on every path. A clear is an exit unless something after it sets the attribute again (a replan). Proven when the retry never refuses, or when an exit can be taken on a refusal: in the gated function itself, or with a refusal reachable after it. Violated when every exit follows success or plans again: a refusal that repeats (a slot window passed, a date changed) keeps the state forever and the gated function does nothing else. The constructor's first value is neither a plan nor an exit. This is question 6's retry bound across calls: `retry-limit` sees a retry inside one call, a loop; a retry held in an attribute and taken by each later call has no loop to see.
- `held-run-recovery` (model over store identity). When a held run writes stores (its retry reaches a writer), the calls the gated function makes before the gate run while it may be held. If they reach writers of the same stores and nothing they reach reads the attribute, they cannot tell the held run's records from a dead run's: a recovery that ends every start without an end ends the held one too. Proven when they read the attribute. The witness names each call and the writers nearest it in call order.

Rule `grow-and-search` (model over loops, in code untrusted input reaches). A loop that searches a list from its start (Rust `.iter().any/all/find/find_map/position/rposition`, or `.contains` on a list the function made; Python `in`, `.index` or `.count` on a list the function made) and adds to the same list in the same loop costs the square of its input: an element with a few thousand attributes holds a core. Asked only in functions the call graph reaches from an untrusted entry: a request handler registered as `.route(path, get(h).post(h2))` (`q6.untrusted_route`, `q6.untrusted_method`; a handler named by path, `post(crate::sso::acs)`, is the one function of that name in that module's file), or a function whose `path:name` matches `q6.untrusted_function` (a vendored parser of request bodies; `[scan] keep` scans vendored code that an exclude would skip). Proven when the function compares the list's length, or the length of the list the loop walks, to anything (`if attrs.len() >= self.max_attributes`). Unknown when the loop walks, or the search reads, a parameter the function does not bound, since a bound at its callers is not followed. A list made inside the loop starts empty on each step and is not asked about. Proven when the list only gains a value of a literal array that it does not hold yet (`let Some(name) = ["KeyName", "X509Data"].into_iter().find(|n| !seen.contains(n))`): it is never longer than the array.

Rule `blocking-unbounded` checks how many requests can run known CPU-intensive Rust operations at once. It uses the same untrusted entry reach as `grow-and-search` and also resolves `crate::module::handler` route arguments. It recognizes XML signature verification through Bergshamra and password hashing through Argon2, bcrypt and scrypt. It follows synchronous calls with exact or single-target resolution from these operations. It asks about inline work in an async function or work in the closure passed to Tokio's `spawn_blocking` or `block_in_place`, a standard thread spawn, or Rayon's global spawn. A violation names the dispatch or inline call and the CPU-intensive operation when the modeled path has no admission control.

The rule proves a concurrency bound when a successful semaphore acquisition precedes the work in the same block and the permit stays live through synchronous work or moves into the detached worker. This assumes Tokio's permit semantics and a fixed capacity on the same semaphore across requests. For an Arc cloned from a state field, the code must declare a Tokio semaphore field with that name. The proof assumes that requests share the state instance. Rayon's global spawn is proven under the fixed worker count of its global pool. These proofs concern running work. They do not establish a limit on the number of queued requests or a suitable worker count.

Admission elsewhere on the modeled call path is unknown when the rule cannot establish its effect and lifetime. Custom pools, channel-to-worker flow, callbacks forwarded through wrapper functions, unresolved call targets and CPU-intensive APIs outside the recognized set can escape the rule. It does not infer global request limits from runtime or proxy configuration.

Rule `untrusted-store-size` (Rust). Request data from a routed handler or a configured entry can set the size of a durable record. The rule follows request payloads through local bindings, resolved calls, error payloads and string formatting. `q6.store_write` matches the full callee text. The default matches `audit`, `insert`, `execute` and `write` on store or database receivers. A violation names the write and the lines that carry request text into it. A proof names a bound on each request-derived contribution, such as a literal `String::truncate` limit, a literal `.chars().take(n)` collected into text, a length condition on the written value or a literal precision in a string format. A fixed audit message has no request-sized contribution.

The rule assumes the configured writer persists its payload, the identified request extractors admit outside data, and the modeled standard-library and parser operations have their usual semantics. A literal SQL `DELETE` uses its arguments to select rows. Required `FromRequest` or `FromRequestParts` extractors matching `q6.authenticated_extractors` reject unauthenticated requests by assumption. A resolved `HeaderMap` guard matching `q6.authenticated_calls` authenticates the continuing path when its error is propagated with `?`. The question asks for a field or record budget. An input envelope limit on a packet, document or request body leaves the size of each field up to the sender. Character limits allow up to four UTF-8 bytes per character.

Known unknowns for `untrusted-store-size` include opaque transforms, unresolved dispatch and caps computed at runtime. The model does not infer limits from database schema, server configuration or transport settings. It does not model route middleware authentication, general Rust trait dispatch, data stored through arbitrary mutable references, or loops that require more than one iteration to reveal a flow.

Rule `emitted-bytes` (Rust, opt-in with `q6.emitted_bytes = true`). One document verification has one allowance for canonical bytes forwarded to any buffer or digest. A violation traces request-derived bytes that can be emitted repeatedly as the number of visits grows independently of their length. The Bergshamra 0.12.0 summaries connect the SAML response to an inherited namespace URI, its repeated lookup after the renderer restores ancestor state, its escaped write and the reference digest. Cargo dependency selection and source fingerprints identify the reviewed vendored and patched copies; a reached verification whose manifest selects another bergshamra-dsig version, or whose sources differ from the reviewed ones, is unknown. Request reach starts at a route or a library boundary declared by `q6.untrusted_function`. For directly declared Rust functions, the rule also checks the closed shape of a byte slice appended unchanged to a local standard-library vector across independent request-slice loops.

A Bergshamra proof assumes the reviewed Cargo selection and source apply at runtime. Every admitted streaming reference, buffered reference and SignedInfo pass must share the same non-resetting allowance. Each slice and byte must be charged before forwarding, reservations must be capped, exhaustion must propagate through the final write, and unsupported transforms must be refused before generic fallback. The SAML proof covers the single context initialized from the decoded length with saturating arithmetic. The direct Rust model checks the entire function body for a single countdown and a rejecting check followed by a decrement before every write. It assumes one invocation represents all passes and the slices at the boundary are independently request-sized.

Opaque writers, changed summaries, an unresolved fallback and a missing budget identity yield unknown at a modeled candidate. Other libraries and other renderer shapes are outside the model. CPU spent before a write, traversal, retained memory and per-key signature work have separate bounds.

Rule `prefix-work` (Rust, opt-in with `q6.prefix_work = true`). A document must have a fixed bound on the prefix-list work added to each element visit or a cumulative allowance charged for every prefix visit, including visits that emit nothing. The rule answers separately for the SignedInfo CanonicalizationMethod and the reference's exclusive transform before SignatureValue verification. The reviewed Bergshamra 0.12.0 paths collect the list into a prefix set, iterate it on visible elements and check namespace membership on filtered invisible elements. The `#default` check on that filtered path searches the prefix set. The admitted SignedInfo and reference node sets carry no namespace filter.

The SAML proof assumes the reviewed Cargo selection, caller, parser, verifier and renderer apply at runtime. Every signature passes its shape gate before the same immutable document reaches the verifier. Both shape checks propagate rejection. The gate refuses extra or namespaced attributes, so the validator and verifier read the same `PrefixList` at each site. Both agree on the tokens for an accepted list of up to eight distinct ASCII NCNames or `#default`, each at most 64 bytes. A document envelope ceiling still leaves the list work per visit request-sized. The SignedInfo shape fixes the visible element count, while the reference target can grow independently of the list. The proof covers the prefix-list contribution to rendering. Document traversal, namespace URI processing, output size and per-certificate verification have separate costs. An output byte allowance alone establishes the emitted-bytes property when its own conditions hold.

Request reach starts at a route or an entry declared with `q6.untrusted_function`. At a directly declared Rust entry, the rule also checks a single traversal whose two independent immutable byte slices and standard-library `black_box` body make the repeated work explicit. A literal cap must reject on the same slice before traversal, either locally or through a checked helper whose error propagates with `?`. A single countdown before the traversal can instead pay before every inner iteration. An unchecked result, conditional or late comparison, check of a different slice, or debit conditional on output supplies no proof.

A reached Bergshamra verifier is unknown when its version or source fingerprint is unreviewed, dispatch cannot be resolved, or the model cannot establish attribute identity and refusal before use. Arbitrary nested loops, other libraries and opaque work accounting lie outside the model. The rule stays out of the default gate.

Assumptions: resource patterns name every durable resource; retry loops are recognized by shape; a held state's refusal is a literal False or None, and a return of anything else settles it. A length comparison bounds the list (its limit is not checked to be small).

Known unknowns: repeated work outside the prefix-work models, retained memory amplified by cloning a value per element, output amplification outside the emitted-byte models, and a nested inner loop's search against an outer loop's growth. Unmodeled calls into another crate (such as a vendored parser) use `untrusted_function` to declare their entry points. Other unknowns are Python request handlers, state machines held in data such as a table of transitions, and held state in a Rust `Option` field. The held-state rules extract conditions and exits from Python. The acceptance set uses no Kani model.

## 7. Proof by effect

Proves: a liveness or success check reads the state it claims. A reply that is true whatever the state proves nothing. Rule `weak-probe` (patterns): `os.kill(pid, 0)` and `os.killpg(pid, 0)` succeed for a zombie or a member that moved group.

Assumptions: weak-probe patterns name the probes whose reply cannot show the state.

Rule `pipe-masks-exit` (model over shell pipelines). A test or lint runner (`pytest`, `ruff`, `mypy`, `cargo test` and `clippy`, `npm test`, `make`, a `*check*.sh`, and others) piped into another command (`| tail`, `| grep`, `| tee`) in a shell script, a workflow `run:` block (`.github`, `.gitea` or `.forgejo/workflows`) or a Makefile recipe. The pipeline's status is its last command's, so a failing runner reads as a pass. Proven when `set -o pipefail` (or `set -euo pipefail`) comes before it in the same block, or `PIPESTATUS` is read after it; a workflow step with `shell: bash` runs with `-eo pipefail`, and a Makefile whose `.SHELLFLAGS` holds `pipefail` sets it for each recipe line. Workflow blocks and recipe lines are parsed as bash on their own lines, each block its own scope.

Rule `random-property` (pattern over Hypothesis settings). A `@settings(...)` decorator or `settings.register_profile(...)` with `derandomize=False`: the property draws new examples on every run, CI included, so whether it passes, or kills a mutant, can change between runs. `derandomize=True` is proven. Without the argument nothing is reported: under `CI` Hypothesis derandomizes by default. Only `@settings(...)` decorators are read as calls; other decorators stay text.

Rule `path-patch-advisories` (manifest entries against advisory checks). A crate replaced through `[patch]` with a `path` or `git` source, or a dependency taken from git (dev-dependencies excepted), in a `Cargo.toml` or in the new side of a diff that edits one (a `.patch` or `.diff` file applied to another project's manifest), in a repository whose shell runs an advisory check (`cargo deny check` with no check named or `advisories` among them, `cargo audit`). A workflow `run:` line that runs cargo-deny or cargo-audit other than as a plain `cargo` command, such as a pwsh step calling a downloaded `cargo-deny.exe`, is read as an advisory check by its text, since run blocks are parsed as bash. Both match advisories by a registry crate's name and version, and a path crate has no registry source, so the copy that is built is never checked and the check passes without it. The witness names each advisory check in the repository. A `path` dependency outside `[patch]` is taken to be the workspace's own crate. Proven when a crate of the repository passes cargo deny `--metadata-path` together with `check advisories` (its code holds both literals) and a shell step runs it (`cargo run -p <crate directory name>`): such a tool can hand cargo deny the resolved graph with each path and git crate given its crates.io source, as `tools/deny-patched` does; that the rewrite covers every such crate is the named assumption.

Known unknowns: a read-back after an effect is outside the model; a probe outside the patterns is not seen. A vendored copy of a published crate taken as a plain `path` dependency is not told from the workspace's own crate; a diff hunk that starts inside a `[patch]` table without its header line, and an advisory check run by a workflow action (`uses:`) rather than a shell command, are not seen. A runner started through a variable (`$TEST_CMD | tail`) is not recognized; a workflow's `defaults.run.shell` is not read.

## 8. Tests that can fail

`proofscan mutate --diff BASE --test CMD` negates each condition the diff adds or changes, and removes each guard exit, `raise`, `bail!`, `ensure!` and `assert!`. Each mutant runs in a pristine copy of the commit (`git archive`). The test command must pass on the unmutated commit first, or every mutant is unknown.

- killed: proven, a test fails on the mutant;
- survived: violated, no test checks that rule;
- timed out or failed to build: unknown.

Each changed `if` condition is also replaced by `True`, the guard taken every time, which negation does not cover: a check that only skips a duplicate is killed by its negation even when no test needs it. Each operand of a changed `or` is also replaced by `False` and each operand of an `and` by `True`, recursing into operands that are themselves conditions, so a guard with two halves shows which half no test needs (ha-loops 0.18.0 review: `key_day != commit_day.isoformat()` in `key_day != ... or key_slot != commit_slot`). `--list` prints the mutants without running anything, and `--at FILE:LINE` (repeated or comma separated) keeps only the mutants on those lines, to recheck a review's survivors without the whole diff.

The tests run with `CI=true`, as CI runs them, so Hypothesis draws the same examples unless a test sets `derandomize=False`. A mutant failed only by such tests (pytest's `FAILED` lines name them, and their decorators are read) is not a stable kill: with pytest they are set aside with `--deselect` and the rest run again, up to three times. If the rest pass, the mutant is violated and names the random tests; another run may let it through.

It runs only on a diff, never across a whole sweep. Assumptions: the test command exercises the changed rule; a mutant that does not compile is not counted.

## 9. Release on every exit

Proves: a resource the process holds (a lock, a holder attribute, a temporary file; `[[q9.resource]]`) is released on every exit, a raise and a cancellation included. For the Rust state check, a modeled error leaves the tracked bookkeeping field unchanged.

Rules (model over the extractor's block structure):

- `release-interrupted`. A release inside a `finally` block that a call in the same block runs before. If that call raises or its await is cancelled, the release never runs. Proven when nothing before the release in its block can raise; a nested `try` inside the block counts as catching what its body raises.
- `release-on-error`. A release on the ordinary path, outside any `finally`, with a call between the acquire and it in the same function. Proven when nothing between them can raise, or when the same function also releases in an exception handler (assumed to catch everything, cancellation included).

- `release-on-panic` (Rust). A handle assigned from a call and released later in the same function by an explicit C release through its bindings (`ffi::`, `sys::` or a `*_sys::` crate path, a name ending in destroy, free, close, release, dispose or delete). A Rust call between them can panic, and a `?` between them returns early, so the handle leaks. Violated with those calls as witness; proven when only calls into C (the release's own prefix, or an `ffi::`/`sys::` path), constructors and pointer or state reads (`as_ptr`, `is_null`, `is_err`, `len`) lie between. A guard whose `Drop` releases the handle releases nothing by hand in the function, so it draws no finding.
- `error-keeps-state` (Rust). In a method returning `Result` with `&mut self`, follows direct field edits and error exits through blocks, branches and match arms. A violation names the field edit and the `?` or `Err` exit that keeps it. A proof names the ordering or the rollback that preserves the field on every modeled error path. Rollback assigns the field's saved entry value back, including in a direct `map_err` closure. The question applies to a count with an increment and either a reset or a related buffer update. Its guard must control a write to the count or a fallible step. The question also applies to collection edits paired with a separate fallible operation on the same field. Fields named for metrics, telemetry or logs are excluded.

A call is not counted when it is the condition deciding whether to release (`if os.path.exists(tmp): os.unlink(tmp)`), when it only reports (`q1.report`), or when `q9.no_raise` names it (path and type helpers, `contextlib.suppress`). Patterns match a callee, a literal argument (`arg:`), or an assignment written `target = value` (`assign:`, for holder attributes cleared with `= None`), each optionally limited to a language.

A resource that outlives the process (a vCenter snapshot, a hot-added disk, a cloudhook) is question 6's `durable-exit`: on every path from a start to the code that makes it, a sweep that releases what earlier runs left must run first (dominate it). A resource's `sweep` pattern names those sweepers (a reconcile); without it, any function that can release the resource counts, which also counts a cleanup that frees only its own. When no start path reaches the code, the answer is unknown.

Assumptions: resource patterns name every acquire and release; any other call can raise or, in async code, be cancelled.

Known unknowns for resource release: a release in a context manager's `__exit__` is not followed; a resource handed to another function or task is not tracked across the call; "for every key" sweeps (a per-VM sweep that misses a VM never run again) are not expressible.

`error-keeps-state` assumes direct fields are independent and recognized collection operations have their usual effects. Interior mutability, custom operators and destructors are outside the model. The rule reports unknown when a helper or borrow may change or restore a field, when a fallible collection edit may update it before failing, or when an earlier check on the same receiver and arguments may rule out a later insertion error. Loops, match guards, macros and paths beyond the branch budget can also require an unknown. Whole-method atomicity and external effects need their own evidence.

A guarded batch can validate the incoming row, flush without arguments, and reset the count before the fallible insertion of that same row. The proof assumes validation is read-only and refusal leaves the buffer intact. Changes kept across the later error carry none of the method's arguments, and each bookkeeping write follows the successful `?` of the operation it records. A completed call on state from earlier calls is not undone by a later error of this call. An insertion before a fallible flush still violates the rule when it keeps the caller's input, even when the count records a successful insertion. The rule follows simple local bindings and copies of arguments. An unresolved alias, helper call or closure carrying data into a mutation leaves the verdict unknown.

## 10. Secrets never reach a sink

Proves: a value derived from a credential does not reach a log or print, a child process's argument list, error text, or the output of a shell command.

Sources (`q10.source`, `q10.env_read`): a call given a credential store's path as a literal (`.storage/`, `secrets.yaml`, `credentials.json`, `.env`, an SSH private key, a `.key` file), and an environment read whose literal key names a secret (`token`, `password`, `api_key` and the like, `q10.secret_name`) but not where one is (`TOKEN_FILE`, `API_KEY_PATH`, `q10.not_secret_name`). A call that only makes a path (`Path("master.key")`, `os.path.join`, `q10.path_call`) is not a source: the path is not the credential. A reader (`read_text`, `open`, `json.load`, `q10.read_call`) whose receiver or arguments hold a store path literal is. A repository declares its own, such as a reply from an API that returns settings (`acceptance/configs/ha-ws.toml` makes the Home Assistant websocket reply one).

Flow: the credential is a value kind like question 1's clock readings. It follows assignments, returns and argument binding, and passes through a call with no in-repo target only when that call carries its input into its result (`q10.carry`: string methods, encoders, `json.dumps`, `format`), so `json.dumps({"reply": reply})` carries `reply` and `requests.get(url, headers={"Authorization": token})` returns a response, not the token. An object built with a credential is not the credential: `Client(token).status()` is clean. A sanitizer (`q10.sanitize`: `len`, a hash, `redact*`, `mask*`) ends it. For this kind only, a variable or call inside a nested call's arguments, and a call's receiver, reach the outer expression through that call's result, so `json.dumps({"reply": redact(reply)})` is clean.

Rules:

- `secret-sink` (model). A sink call (`q10.sink` plus question 1's report calls: `print`, logger methods, `subprocess.run` and the other process starters, an `...Error(...)` constructor, `sys.stderr.write`) whose argument carries the credential kind. Keyword arguments others do not read are skipped (`q10.not_sink_kwarg`: a child's `env=` and `input=`). The witness lists the source reads in the same function, or says the value arrived from outside it. A source that reaches no sink is reported proven with its assumptions.
- `store-printed` (model over the shell parse). A shell command that prints what it reads (`q10.print_cmd`: `cat`, `head`, `jq`, `grep` and the like; a wrapper such as `ssh` or `sudo` when its command is one), given a store path, whose output is printed. `grep -q` and `sed -i` print nothing (`q10.quiet_arg`). The output is printed when it is not inside `$(...)`, not redirected to a file, and not piped into a command that prints only a length or a digest (`q10.pipe_sanitize`: `wc`, `sha256sum`, `jq '... | length'`).

Assumptions: source patterns name every credential read; a sanitizer returns no part of the value; a value is not passed on through a subscript, an attribute store or a container method the model does not follow.

Known over-reads: a mapping that holds a credential (a child's `env` dict, a settings dict) carries the kind into every lookup in it, so reading its `PATH` entry counts. On a sweep of 128 repositories this was 34 of 40 violations, all in one codebase and its build copy.

Known unknowns: a key read by subscript (`os.environ["TOKEN"]`, `reply["password"]`) is not a source; values that cross a file or process boundary; Rust and JavaScript sinks beyond the shared report patterns; a store read through a path built at run time or held in a variable (`open(KEY_PATH)`).

## Policies (SMT)

`proofscan policy --kind brief|sudoers|rules --candidate A --reference B` (feature `smt`, links libz3) asks Z3 for a request A allows and B denies. Unsat proves A grants no more than B. Sat gives the request and the line in each policy that decides it. Unknown names the solver's reason or the construct not modeled (a sudoers alias). The reverse direction is reported as the requests only the reference allows.

- brief: `Writable:` and `Read only:` lines, deepest line decides, anything else not writable; `\` read as `/`, case-sensitive.
- sudoers: user specifications, last match decides, `!` denies, a command named without arguments allows any, `""` allows none; aliases are unknown.
- rules: TOML with `semantics` (`first-match`, `last-match`, `deny-overrides`), `default`, `[fields]` typed `string` (glob, `*` crosses `/`), `int` (value or `a-b`) or `ipv4` (address or CIDR), and `[[rule]]` with `effect` and `match`.

## Review focus

`proofscan review --diff <base>` turns the verdicts on a change into a reviewer's brief. Unknowns are the scope: constructs no proof covers, each named. Violations are handed over as found. Proven sites come with the assumptions each proof rests on; a reviewer re-raises one only by naming an assumption that fails, which is the settled-decision rule applied to proofs.

With `--findings`, each reviewer finding is checked against the verdicts within two lines of its `file:line` (its site or a witness step):

- `confirmed-by-violation`: a violation is there.
- `contradicted-by-proof`: a proven verdict is there. The rejection is backed by that proof for its question only; a finding about another property is not touched by it.
- `unknown-here`: the scanner reached the construct and could not decide it.
- `no-proof`: nothing is there; the finding stands on its own evidence.

What is proven: the check is exact against the scanner's verdicts. What is heuristic: matching a finding to a verdict by line, since a reviewer and the scanner can name different lines of one statement. What stays unknown: whether a finding's claim is the question's claim, which a person reads from the finding's text.

## The escaped-defect loop

A defect that got past review is a case in a shared escaped-defect file (`review-eval/cases.toml`). `proofscan accept` reads that file as it is: `clone` is the repository, `review_at` the commit, `fix` the fixing commit, `files` the defect's files. A defect with no `expect` is an open row. Its candidates are the violations in its files at `review_at` that are gone at `fix` (matched by question, rule, file and message, since lines move) or that sit on a line the fix changed. "None" means the case as written does not show the defect: a narrow scope, a fix that kept the construct, or a defect no question covers, which is the signal for a new rule or question. Open rows are reported and not counted, so the shared file never fails the acceptance run. Classing a case means adding its `expect`, with the answer key's lines, to the acceptance cases file, where it is then required.
